# T1.5 → T2 → T3：实测结论

本轮完成了真实两机完整模型执行、正确性验证和受控offload对照。**没有找到四等分接力相对调优且充分预取的连续切层的稳健优势。** 接收端权重提交会显著拖延小activation；控制在途工作可以缓解它，但“activation早到”不等于完整请求更快。

## 1. 小activation为什么变慢

T1.5 对1.3B b1 q1/128、双方向，分别运行无背景、仅发送端、仅接收端、两端背景；每活跃端固定搬运两遍完整block并执行后续计算。148配置×10正式样本，权重字节量不变。

q1、零额外到达延时的P50：

|背景|A→B activation ACK完成 ms|B→A activation ACK完成 ms|
|---|---:|---:|
|无背景|0.317|0.316|
|仅发送端bulk H2D|1.006|0.991|
|仅接收端bulk H2D|8.618|16.111|
|两端bulk H2D|8.564|15.911|

主要退化来自**接收端已排入的权重工作**。仅接收端时，activation的copy调用P50约0.012–0.015ms，但完成等待约7.679/14.991ms。相同GPU时钟上，bulk情况下activation开始事件在所有背景权重完成后出现的样本为A→B 8/10、B→A 10/10；分块策略均为0/10。它不只是线程启动的固定开销。

把到达延后2ms，接收端等待约降至5.454/12.826ms；随机0–8ms相位下约3.510/10.872ms。到达相位影响剩余排队，但不改变接收端干扰主导的观察。

这是提交队列/复制资源调度的有力证据；没有CUPTI/驱动内部跟踪，尚不能把全部等待精确划给物理DMA、驱动调度或线程唤醒。此处固定两遍权重，旧T1是持续背景，因此不要求复现旧4.405/8.107ms的精确数值；新协议无背景时间也不能与旧0.162ms直接混比。

## 2. 控制预取有效，但有代价

同样q1、两端背景、固定等量权重：

|策略|A→B activation ms|B→A activation ms|A→B：发送/接收端完整有限工作 ms|
|---|---:|---:|---:|
|bulk|8.564|15.911|16.604 / 9.201|
|8MiB，单在途|0.649|0.957|17.346 / 10.060|
|8MiB，最多两个在途|0.792|0.828|17.075 / 9.557|
|8MiB，activation提交时优先|0.561|1.086|17.861 / 10.173|

activation显著变快，但加载同样权重和后续计算所需的端点时间未一致缩短：例如A→B的window2端点时间分别增加约2.8%/3.9%，priority增加约7.6%/10.6%。一部分等待移到了计算取权重之前，同时分块/流控损失权重吞吐。表中是各端本地完成时长，不把两端未校准的时间取max伪装成精确全局makespan。

所有q128对照、相位、分阶段耗时、GB/s和负结果见 [T1.5完整报告](results/t15-summary-01/README.md)。控制策略在T3同时提供给C1/R1；补充完整请求的bulk消融见文末。

## 3. 两机完整模型正确性通过

共享执行器使用真实全局层号与原FlexGen计算；覆盖单机完整模型、两机连续、四组交替，以及resident/demand/prefetch。125M先通过，再验证1.3B。真实有效prompt包括32/128/256，batch1/4；未把padding算作有效上下文。

预先固定atol=0.02、rtol=0.01，token必须完全一致。每层检查KV长度、写入位置和K/V各256个均匀采样值。T2逐步核验；T3将数值检查移到计时外。本轮正式结果中，logits和KV抽样最大差异均为**0**，token完全一致；不声称全部KV逐元素比较。

另验证了125M不等长分组 `[0,2), [2,5), [5,9), [9,12)` 的常驻、按需和预取，避免“重复前几个block”替代完整模型。buffer检查确认copy-ready先于计算、槽位覆盖晚于上次计算结束。

## 4. R1没有胜过调优C1

主矩阵144配置，每配置1次warmup+3次正式请求，覆盖两个模型、双方向、三种负载、C0/R0/C1/R1和常驻。C1按25/50/75%扫描切分，R1四等分；两者均提前预取，策略与每端slot字节相同。以下选同为window2的结果，时间为**完整请求**，含embedding/head/token返回：

|模型/负载|方向|最优C1首节点层比例|C1 ms|R1 ms|R1相对C1|
|---|---|---:|---:|---:|---:|
|1.3B b1,q32,gen8（decode为主）|A→B|25%|620.08|755.73|慢21.9%|
|同上|B→A|75%|617.89|783.88|慢26.9%|
|1.3B b1,q128,gen4|A→B|25%|316.14|382.90|慢21.1%|
|同上|B→A|75%|312.00|398.28|慢27.7%|
|1.3B b4,q256,gen4|A→B|25%|378.09|403.98|慢6.8%|
|同上|B→A|75%|320.74|439.04|慢36.9%|
|125M b4,q256,gen4|A→B|50%|40.80|79.60|慢95.1%|
|同上|B→A|50%|50.94|69.07|慢35.6%|

1.3B最优切分在两个方向都把18层给H2D较快的B，6层给A。结论在交换起点后保留。只比较平均12/12会误判：例如A→B b1,q128 window2，平均C1为388.29ms，R1为382.90ms，看似接力略快；调优连续后变为316.14ms。

125M A→B小prefill是最接近盈亏边界的点：priority初测C1/R1为31.82/31.29ms，约1.7%差异。额外交错顺序复测每臂18次，整体中位数31.57/31.09ms，但R1明显长尾，6个配对case中位数比的描述性bootstrap区间约0.723–1.071，包含1；且换方向后优势消失。**不能把这个微小差异当稳定正收益。** 复测原始样本及方法在 `results/t3-confirm-125m-a-b-01/confirmation.json`。

## 5. 收益/退化来自什么

提前预取本身有效，且连续基线同样受益。1.3B A→B b1,q128：C0约614.88ms，R0约633.07ms；平均切分C1约388.29ms，R1约382.90ms。两端H2D可以并行，时间线对C1/R1都提供证据，不能把它归为接力独有。

R1某些配置的“等待权重”列更小，却没有相应端到端收益：同一例中首节点weight host wait从平均C1约320.43ms降到R1约46.47ms，但请求总时间只差约5ms。该等待被输入activation/其他依赖等待替代，不能把各列差值相加宣称节省了274ms。

R1每步有3次activation跨机，连续只有1次；应用层activation字节精确增加为3倍。大prefill产生明显额外成本。预取跨prefill/decode连续运行，短请求中某些decode步可能受预先完成的搬运帮助；不能从某个decode阶段较快推断稳态吞吐或整个请求更快。

同模型offload每端weight-slot固定为125M约81.1MiB、1.3B约1.126GiB；endpoint和KV另记。统一PyTorch CUDA分配器上限4GiB，正式分布式峰值allocated约1.575GiB，RSS采样峰值约6.68GiB。RSS含pinned缓存与前序参考分配，不能等同活跃张量字节。

## 6. 适用边界与限制

本轮**未找到稳健适合接力的负载**。125M A先执行的小prefill仅接近盈亏边界，缺乏稳健优势；大activation和1.3B在异构切分可调的条件下均不支持采用当前四等分接力。不能据此否定其他模型容量、组大小或硬件下的可能性。

两模型都能自然全GPU驻留。A上单机参考的1.3B b1,q128,gen4约35.28ms，两机连续常驻约40.60ms，而最佳受控offload C1约316.14ms。常驻基线保留；offload故意按步重载，未使用跨步权重保留。这些不是实际部署必要性或成本收益证据。

主矩阵重复次数少、顺序固定，最优cut来自同批数据，存在波动和选择偏差。所有负结果和诊断轮次保留；旧priority在网络等待期间过早暂停的01轮次已明确排除，修复后02轮次完整重跑。跨机时钟仅有不确定区间估计，不画精确对齐的全局轴。

本轮不做在线SLO、成本或创新性结论。下一步若继续，应先研究容量确实受限时的分配/驻留策略与更少通信的布局，不应将chunked prefill或在线调度的其他收益混入当前接力结论。

## 7. 补充：控制提交有没有完整请求净收益

对1.3B b1,q128,gen4固定布局/切分，额外比较bulk、window2和priority，每配置3次正式请求；先通过bulk数值门槛。C1固定为主矩阵选出的A→B cut25%、B→A cut75%，R1仍四等分。T3的bulk是一整个group平坦拷贝，与T1.5逐张量bulk的粒度不同。

|方向/布局|bulk E2E ms|window2 E2E ms|priority E2E ms|
|---|---:|---:|---:|
|A→B C1|317.47|315.54|324.53|
|A→B R1|385.86|382.18|392.29|
|B→A C1|308.36|311.58|324.79|
|B→A R1|398.72|397.49|391.08|

结果没有一致的净收益。window2相对bulk的变化约−1%到+1%，小样本下不足以认为稳定改善；priority对C1有明显代价，在R1则方向相关。降低小activation延迟不能自动推导更短完整请求。

代表性A→B R1请求的各步耗时：bulk约 `[150.98, 43.71, 142.77, 48.03]`ms，priority约 `[104.47, 93.42, 95.32, 98.59]`ms；首步变快、后续等待重新分布，总时间385.86→392.29ms。预取跨步连续运行，因此不能用decode步的中位数乘步数推导请求时延，更不能从某个短步声称稳态吞吐改善。

完整消融见 [控制策略报告](results/t3-control-summary-01/README.md)。本轮的结论是：控制在途预取能缓解接收端activation排队；代价是权重吞吐/调度开销及等待位置变化，端到端必须单独测量。
